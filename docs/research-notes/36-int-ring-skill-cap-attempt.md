# 36 Intelligence ring and the skill cap: what the engine does, and why we stopped

Goal: an Intelligence ring/necklace ("Klug", player effect 22, DB effect 10) should raise the wearer's skill cap like base Intelligence does, and taking it off should lower skills again so the ring cannot be abused. Result: the cap bonus and the display worked, the loss on unequip never did, so the idea was dropped (the ring got another buff, see note 37).

- **The engine builds the cap only from the base stat.** `_calcSkillCap` (server RVA 0x344cb0) = group cap from `world_1.xml` + (Intellect - baseline) * 20,000,000 units; it is evaluated at login (character-info init 0x1bf760) and by `onStatChange` (0x349820) when the base stat changes. Item effects never reach it: the ring showed the effect icon with magnitude 10 but the cap stayed.
- **GM accounts show 3000.** `_calcSkillCap` returns 30,000,000,000 (3000 points) when the account has the "unlimited skills" access bit, but only once the player is online; every live recalculation (`/SETMYSTAT`, `/EFFECT 22`) therefore showed 3000 for a GM and a relog showed the real number. Test with a non-GM account.
- **Cap bonus on the server** (`tools/patch_int_cap.py`): `getMaxSkillAmount` (0x347650) is the single place every cap check uses; a wrapper in a new section adds `magnitude(effect 22) * 20`. Effect storage: cObjEffects = player + 0x11D8, entry = +0x60 + id*0x18 (+0 expiry, 0xFFFFFFFF = unlimited; +0x10 i64 magnitude, 1e6 fixed point). The player comes from `FUN_140134850(charId, 0)` (0x134950 returns the net connection, not the player). Confirmed: a tester raised a skill above the shown cap.
- **Cap display on the client** (`tools/patch_int_cap_client.py`): the skills window shows `getMaxSkillAmount` (client RVA 0x4d4d80) through `updateMaxSkillcap` (0x4d5d40/0x4d7380), but only recomputes when the server sends its table (login, before the ring effect exists). The client entry of effect `id` is at player + 0x1A30 + id*0x60 (expiry +0x48, magnitude +0x58); effect 22 = player + 0x22B8/0x22C8. A first attempt used the effect-25 entry (player + 0x2390) as the container and read nothing. The wrapper adds the bonus, a hook on the effect-change notifier (0x936d50) and on the skill update (0x4d72f0) refreshes the window. Confirmed: 896 with the ring, 876 without.
- **Login trim.** The character-info init calls `checkMaxSumSkillAmount` (0x346610) at 0x1bf925 before the equipment effects exist, so a login with the ring lowered skills by the bonus. Switching that call off (5 NOPs) fixed it. The engine still trims on every live cap drop.
- **What never worked: trimming on unequip.** `checkMaxSumSkillAmount` is the right tool (lowers only skills with the down arrow, split evenly). Unequipping fires `cObjEffects::ChangeEffectMagnitude` (0x4dc9b0, mode 1 = subtract); the hook runs, but the safety check "character online" (`FUN_140134850(charId, 0)` with the id read from the effect owner's vfn+8) returned 0 although the player was online, so the trim was skipped (server log lines `[IntCap] ... character not online`). A logout fires the same removal event, so such a guard is mandatory. Never solved; swapping rings, death (`RemovedOnDeath`) and potions with the same effect would have been further holes.
- **Method that worked:** hook functions through a new PE section (code cave) with the original prologue copied behind a `jmp`; keystone assembles, capstone checks; the engine log function (0x405090) and `snprintf` (0x85d90) give `[IntCap]` lines in the server log for diagnosis.
